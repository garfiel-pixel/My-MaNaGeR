FINDING 2 — MEDIUM: R2 Project Data Has No Application-Layer Encryption
================================================================================

CURRENT STATE:
- Project state stored as plaintext JSON via R2.put(key, JSON.stringify(next))
- Changelog snapshots: same plaintext JSON
- Review proposals: same plaintext JSON
- User prefs: same plaintext JSON
- Cloudflare provides SSE (server-side encryption at rest) at infrastructure level
- The app already has AES-256-GCM encryption for Google Drive backups
  (js/mmgr-google-auth.js: encryptPayload/decryptPayload with PBKDF2 key derivation)

WHAT THIS MEANS FOR COMPANY DATA:
- A Cloudflare-side breach (unlikely but possible) would expose all project data
  in plaintext — tasks, risks, budget, schedule, contacts, claims, everything
- For construction companies holding sensitive bid data, financial projections,
  and workforce information, application-layer encryption is standard practice

HOW IT COULD WORK (one approach — owner decides):
- On save: encrypt the state JSON with a project-specific key before R2.put()
- On load: decrypt after R2.get()
- Key derivation: project owner code + salt (already in D1) -> AES-256-GCM key
- The owner code is already transmitted per-request (X-Owner-Code header)
- This is the same pattern the Google Drive backup already uses

OWNER NOTES — How do you want this implemented?
(Encrypt all R2 blobs? Just project state? What key derivation?
 Same AES-256-GCM as Google Drive backup? Per-project key?)

FINDING 5 — INFORMATIONAL: Client-Side State Is Unencrypted
================================================================================

CURRENT STATE:
- Full project state lives in localStorage without encryption
- This is by design — the app is offline-first, the browser IS the primary store
- Google Drive backup has optional AES-256-GCM encryption
- If a device is compromised, all project data in localStorage is readable

NOTE: This is architectural, not a bug. The offline-first design means the
browser is the authoritative store. encrypting localStorage would break the
core offline-first promise. Documenting for awareness only.

WHAT'S ALREADY DONE WELL (no action needed)
================================================================================

1.  API keys never persist — sessionStorage-only, stripped from all server storage
2.  Owner codes use PBKDF2-SHA256 with per-project salts, never stored plaintext

4.  Session cookie is HttpOnly/Secure/SameSite=Lax with HMAC-SHA256 signing

8.  Google Drive backups optionally encrypted with AES-256-GCM + PBKDF2
9.  Rate limiting on every endpoint
10. AI relay is stateless — no key logging, persistence, or echo
11. Secrets stripped from project state before R2 storage (stripStateSecrets)
12. COOP/CORP headers prevent cross-origin window embedding
13. HSTS enforced (max-age=31536000; includeSubDomains)
14. Owner code recovery requires Google session verification
15. Admin panel requires ADMIN_CODE (constant-time comparison)
16. Billing webhook verified with HMAC-SHA256 before any DB write

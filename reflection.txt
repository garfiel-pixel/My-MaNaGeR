SESSION 2026-11-08 - I-1 ROOT-CAUSE FIX: PERSIST OWNER CODE + AUTO-CLAIM

WHAT LANDED (commit 9ccb650 on feature/complete-backlog)

1. I-1 root cause confirmed and fixed. A cloud project created while signed OUT
   is stored with google_sub = NULL on the server. Its only recovery key - the
   owner code - lived in sessionStorage (js/mmgr-cloud.js:124 setCode), which is
   wiped on re-auth. After re-sign-in the code was gone, the project never
   appeared under "My Cloud Projects", and the recovery path (claim) could never
   fire. That is exactly the owner's "my cloud projects are not the ones I
   uploaded" report.
   - Fix (owner decision: "Persist code + auto-claim"): getCode/setCode/
     clearCode now read/write localStorage instead of sessionStorage, so the code
     survives re-auth and reload.
   - Added collectHeldOwnerCodes() (scans every mmgr_cloud_code_<pid> key) and
     autoClaimHeldProjects(): on mmgr:google-signed-in and mmgr:user-changed it
     checks checkMe(), then POSTs /api/cloud/projects/<pid>/claim for each held
     code, then dispatches mmgr:cloud-linked so the dashboard re-fetches. The
     claim is idempotent (already-linked rows return alreadyLinked) and is
     skipped when no session is active.

2. Mirrored the localStorage move to the three direct readers that bypassed
   getCode()/setCode():
   - js/mmgr-cloud-dash.js:205 - open-by-code "owner" seed now writes
     localStorage (was sessionStorage). Editor code seed left as sessionStorage.
   - js/mmgr-ai.js:2069 - MCP project owner code read from localStorage.
   - js/mmgr-presence.js:43 - access-evidence owner code read from localStorage.

3. Server contract for I-1 already proven sound by T-CLOUDLIST (tools/
   qa-cloudlist.cjs, 11/11): anonymous create -> owner code + google_sub NULL;
   account list does NOT see it; claim with code+session links it and it appears
   in the account list AND on a second device (same sub). No server change was
   needed; the gap was purely client glue + the session-only code store.

LESSON WORTH KEEPING
When the same value is read from storage in five places, centralizing it in one
getter/setter is not optional - three of those reads bypassed getCode() and had
to be moved in lockstep, or the persisted code would have stayed invisible to
the parts that needed it. The session-only choice that "protected" the code was
the exact thing that made I-1 unrecoverable.

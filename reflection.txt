## Key Learnings

### Theme System Architecture
1. **Three pages share theme state** — `app.html`, `project.html`, and `admin.html` all
   have inline FOUC scripts that read `localStorage.mmgr_theme`. All three must be
   updated when changing theme behavior. Forgetting one causes inconsistent behavior.
2. **`mmgr-theme.js` is the single source of truth** for theme logic. The inline scripts
   only handle the "before paint" case; the full logic (apply, toggle, persist) lives
   in the JS module.

### CSP Hash Discipline
3. **Every inline script edit requires hash regeneration.** The dashboard logic change in
   app.html (new renderCards function) changed the hash for block #4. The verification
   script caught this — the system works.

### Demo Project Data Model
4. **Demo projects carry a `demo: true` flag** in `projects-data.js`. The rendering logic
   can split on this flag without touching the data source. This is the cleanest
   separation pattern — the data stays unified, the rendering filters.

### Delete + Recovery Flow
5. **Soft delete with grace period** is a standard pattern: set `deleted_at`, filter by
   age on read, hard-purge after grace. The existing `handleCloudProjectDelete` already
   sets `deleted_at` (soft delete), and `handleCloudProjectRestore` clears it. The new
   endpoint just adds a filtered list query.

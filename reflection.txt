## Background — The Crash
The previous session's AI agent ran bash-specific commands (`taskkill //F //IM node.exe`,
`2>/dev/null`, `sleep 12 &`) in a PowerShell session (`PS C:\Users\Garfield\...>`). This
mixed three incompatible shell conventions in one line, causing the terminal to hang for
10+ minutes and dump raw cursor-position escape sequences (`[555;63;30M...`). The agent
then incorrectly blamed "a known miniflare/workerd instability on Windows" — a diagnosis
it never verified — instead of recognizing its own command syntax didn't match the shell
prompt. This incident directly led to the creation of the shell-discipline skill.

## Root Cause Analysis — The Shell Crash
**Shell identification:** The prompt showed `PS C:\Users\Garfield\...>` — native PowerShell.
**Commands sent:** `taskkill //F //IM node.exe 2>/dev/null; sleep 12 &`
**What went wrong:**
- `//F //IM` — Git Bash's double-slash escaping for Windows flags. Invalid in PowerShell.
- `2>/dev/null` — Unix redirection. `/dev/null` does not exist on Windows.
- `sleep 12 &` — Bash job control. PowerShell's `sleep` and `&` behave differently.
**Result:** Terminal hung, then dumped raw escape sequences — a classic terminal
control-sequence desync, not a program crash.
**Diagnosis error:** The agent attributed the hang to "known miniflare/workerd instability"
without any actual error message from those tools. A shell hang with no program output is
evidence about the shell, not about the program being run.

## What Was Accomplished This Session

### 1. Shell-Discipline Skill Created (`.agents/skills/shell aid/SKILL.md`)
A new project-authored skill that governs ALL terminal/shell command execution:
- **Before running any command:** Identify the actual shell from the prompt, not from
  habit or assumption. PS C:\...> = PowerShell. C:\...> (no PS) = cmd.exe.

### 2. Cross-Platform Fix in `verify-controls-admin.cjs`
**File:** `tools/verify-controls-admin.cjs`
**Change:** Replaced hardcoded `C:/tmp/chrome-ctrl-` with `path.join(os.tmpdir(), 'chrome-ctrl-')`.
**Why:** The test used a Windows-specific path that would fail on Linux CI (where `/tmp/`
exists but the explicit `C:` prefix is invalid). Using `os.tmpdir()` makes the test
cross-platform — it returns `/tmp` on Linux, `C:\Users\...\AppData\Local\Temp` on Windows,
and the correct temp dir on macOS.
**Impact:** Enables the controls-admin browser test to run on any OS without modification.

**Fix (diagnostic):** Added error detail logging to catch blocks so the next CI run shows

## Key Learnings

### Shell Discipline (from the crash)
1. **Always identify the actual shell** from the prompt before running any command.
   The prompt is the ground truth, not habit or assumption.
2. **Never mix shell syntaxes** in a single session. Bash double-slashes (`//F`),
   Unix redirection (`2>/dev/null`), and bash job control (`cmd &`) are invalid in
   PowerShell. PowerShell's `taskkill /F /IM`, `2>$null`, and `Start-Process` are
   the correct equivalents.
3. **Garbled terminal output = shell state problem**, not a tool crash. The escape
   sequences (`[555;63;30M...`) are terminal cursor-position commands leaking through
   because the terminal's state machine is desynchronized.
4. **Never invent root causes** for external tools without actual error messages from
   those tools. A shell hang with no program output is evidence about the shell, not
   about the program being run.
5. **Open a fresh terminal** when the shell state is corrupted. Continuing to send
   commands into a desynced terminal makes even correct commands look like failures.

### Cross-Platform Development
1. **Always use `os.tmpdir()`** instead of hardcoded paths in test harnesses. The
   `C:/tmp/` path works on Windows but fails on Linux CI. `os.tmpdir()` returns the
   correct temp directory on every OS.
2. **Test on the target platform** — or at minimum, use platform-agnostic APIs in
   code that runs in CI (which is Linux).

### CI Architecture Understanding
1. **HTTP tests vs browser tests:** The Cloud Phase 1 HTTP tests (C1-C3, C4a, C5)
   use Node.js `fetch()` directly against the wrangler server. The browser tests
   (C4b-C4h) use headless Chrome via CDP (Chrome DevTools Protocol) to navigate to
   the page and interact with the UI. These are fundamentally different execution
   environments — the browser has CSP, service workers, CORS policies, and a
   different fetch implementation.
2. **Error swallowing in catch blocks:** Generic catch blocks that show "Cloud is
   unavailable" without logging the actual exception make CI failures impossible
   to diagnose. Always log the error in catch blocks, at minimum with
   `console.error()`.
3. **Browser diagnostics:** When a browser-based test fails but the equivalent
   HTTP test passes, the issue is almost certainly in the browser environment
   (CSP, service worker, CORS, timing), not in the server code.
